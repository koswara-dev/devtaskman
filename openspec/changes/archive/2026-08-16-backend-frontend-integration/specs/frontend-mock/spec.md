## MODIFIED Requirements

### Requirement: Role Selection and Dashboard Views
The web application SHALL authenticate users against the backend and display customized metrics dashboards based on the authenticated user's server-assigned role (Admin, PM, Dev/QA Leader, Developer, QA Engineer).

#### Scenario: Logging in as a role
- **WHEN** the user submits valid credentials for a seeded account on the login screen
- **THEN** the system SHALL call `POST /api/v1/auth/login`, store the returned JWT, and update the navigation menu and dashboard metrics to reflect that account's role, hiding PM-only administrative controls for non-PM roles

#### Scenario: Switching User Roles
- **WHEN** the user selects a different seeded account from the "Simulasikan Peran" quick-switch panel
- **THEN** the system SHALL re-authenticate as that account via `POST /api/v1/auth/login` and update the navigation menu and dashboard metrics to reflect the newly authenticated account's role, hiding PM-only administrative controls for non-PM roles

#### Scenario: PM Dashboard Overview
- **WHEN** the PM role is selected
- **THEN** the system SHALL display interactive charts representing task status distribution, remaining tasks vs deadline, and team performance metrics, computed from tasks fetched via `GET /api/v1/tasks`

### Requirement: Task Administration
The system SHALL allow PMs and Leaders to create, update, and delete tasks via the backend REST API.

#### Scenario: PM creates a new task
- **WHEN** the PM fills in the task form with title, description, priority (High/Medium/Low), due date, assignee, and clicks "Create"
- **THEN** the system SHALL submit the task via `POST /api/v1/tasks`, and on success render the task returned by the server (initial status "To Do") in the Kanban board

### Requirement: Slack Notification Simulation
The system SHALL display notifications generated by the backend when specific task transitions occur, delivered via the live notification stream and notification history endpoint.

#### Scenario: Notify QA when task is Ready for QA
- **WHEN** a task's status changes from "In Progress" to "Ready for QA"
- **THEN** the system SHALL receive the resulting notification via the SSE stream (or, on reload, via `GET /api/v1/notifications`) and display it as a simulated Slack notification saying "Tugas [ID] - [Judul] siap diuji oleh tim QA"

#### Scenario: Notify Dev when task fails QA
- **WHEN** a task's status changes from "Testing" back to "In Progress"
- **THEN** the system SHALL receive the resulting notification via the SSE stream (or, on reload, via `GET /api/v1/notifications`) and display it as a simulated Slack notification saying "Tugas [ID] - [Judul] gagal uji. Mohon periksa kembali"

### Requirement: Admin Settings and Access Control
The system SHALL allow Admins to manage users and assign roles via the backend REST API.

#### Scenario: Admin assigns role to a user
- **WHEN** the Admin changes a user's role using the role dropdown in the Admin console
- **THEN** the system SHALL submit the change via `PUT /api/v1/users/:id`, and persist the updated role only once the server confirms the update

### Requirement: Import Users via CSV Template
The system SHALL provide a CSV template download and allow Admins to upload a CSV of employee roles to the backend.

#### Scenario: Admin downloads template and uploads CSV
- **WHEN** the Admin clicks the CSV template download and uploads a CSV containing employee names and roles
- **THEN** the system SHALL parse the CSV client-side, submit the parsed rows via `POST /api/v1/users/import`, and populate the user list from the server's response
